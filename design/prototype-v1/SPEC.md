# CHIME 原型说明 v0.1

## 范围和依据

已确认：先做店长日常业务，平台运营单独标注。主要用户是在门店碎片时间操作手机的店长。目标是快速找到顾客，完成开卡、扣次、消费登记和账号管理。

依据：`PRODUCT.md`、`pages.json`、`pages/index/*.vue`、`pages/user/*.vue` 与 `service/`。状态判断来自代码与本地预览，不代表线上权限、接口、数据一致性已验收。demo 组件库页面不纳入产品原型。

## 现有能力与设计建议分开记录

| 范围 | 代码中的现状 | 本版处理 |
| --- | --- | --- |
| 登录 | 账号、密码、图形验证码，已有登录与验证码调用 | 保留，原型使用演示凭据 |
| 经营首页 | 已有消费笔数、开卡会员、新会员、趋势、低余次/到期/未消费提醒汇总 | 保留统计口径，压缩装饰；不新增营业额 |
| 会员 | 查询、分类、筛选、排序、新增、编辑、删除已有调用 | 展开搜索与分类主线；筛选/排序作为后续应补面板记录 |
| 次卡 | 开卡、扣次、补次、设置余额、停用、启用、作废已有调用 | 拆出填写、核对、结果与管理操作 |
| 消费 | 会员档案内与消费统计页有查询和增改删调用 | 统一消费查询入口；独立详情是新增界面承载方式 |
| 消费记录页 | `consume-record.vue` 静态列表与统计，详情仍占位 | 与消费统计页归并为结构建议，不能认定其已有真实数据 |
| 次卡流水 | 列表、次卡与变更类型筛选已有调用 | 保留会员档案内列表；复杂筛选待下一轮展开 |
| 短信 | 配置状态、扣次发送开关、短信日志已有调用 | 演示已配置与排队状态；真实短信不发送 |
| 员工 | 当前店员分页、新增、编辑、密码重置、停启用已有调用 | 完整展开；不新增自定义角色权限 |
| 个人账号 | 昵称、头像、账号只读字段、关于和协议已有入口 | 昵称可演示修改，头像仅表示位置，文档不编造条款 |
| 门店/方案/品牌 | 静态数据、只改本地状态或提示成功，存在 TODO | 归档为平台运营，变更操作禁用 |
| 充值/预约/商品/收款码/客服/反馈 | 未开放、占位或尚无完整操作 | 不进入日常主线，保留范围记录 |

## 信息架构

```text
登录
└─ 四个主入口
   ├─ 首页：概览 / 趋势 / 提醒汇总 / 扣次与开卡 / 散客消费
   ├─ 会员：搜索分类 → 档案
   │  ├─ 次卡账户 → 开卡 / 扣次 / 管理
   │  ├─ 消费记录 → 详情 / 编辑 / 删除
   │  ├─ 次卡流水
   │  └─ 短信日志
   ├─ 工作台
   │  ├─ 消费查询 → 详情 / 新增散客消费
   │  ├─ 员工管理 → 新增编辑 / 停启用 / 密码重置
   │  └─ 平台运营范围说明 → 门店 / 服务方案 / 品牌（演示）
   └─ 我的：个人资料 / 账号与关于 / 文档 / 退出
```

结构建议：取消全局中央加号；常用业务由首页和当前页面承接。门店/员工管理集中在工作台。消费记录与消费统计收拢为消费查询。会员列表不展示删除按钮，编辑内进入确认。

## 关键流程

### 1. 会员扣次

首页扣次 → 搜索选择会员 → 选择可用次卡 → 填写次数、消费时间和备注 → 可选短信通知 → 核对对象与扣后余额 → 提交中禁用连点 → 结果 → 会员档案。

规则：扣减次数为正整数，不超过可用余次。已过期、停用、作废、余额不足的卡不能发起扣次。编辑原消费时，需先回补原扣次，再核算新扣次；可用量包含同卡原记录回补。

失败：保留填写内容与会员上下文，可重试或返回修改。成功：余额、消费记录与流水同步。短信排队不是发送成功，发送失败不能撤销已完成的扣次。

### 2. 新会员与开卡

会员列表新增 → 姓名/手机选填，微信昵称/微信号/来源必填 → 建档成功 → 档案开卡 → 卡名/次数/有效期/备注 → 成功 → 次卡账户。

卡名与总次数必填，总次数 1–9999。有效期按原系统可选。原型以手填卡信息为准，不依赖尚未接入的服务方案。原型要求新开卡有效期不早于演示营业日，是新增的防错建议。

### 3. 卡项调整

档案 → 次卡管理 → 补次或手工调整 → 显示当前余次 → 填写变更数值和原因 → 保存 → 结果和流水。

补次是在原余次上增加；手工调整是直接设置余次。原因必填是新增建议，需业务确认。停用可重新启用；作废不可恢复。删除有关联业务的会员由服务端决定，原型采用阻止删除的保守演示规则。

### 4. 消费查询与更正

工作台消费查询 → 日期/姓名或手机/消费类型 → 消费详情 → 编辑或删除。新增散客消费需要姓名，手机号选填；类型保留抖音新客福利、美团团购、纹绣、眼线；有会员的非次卡消费从档案登记。

消费时间和备注保留。不引入支付、金额、退款字段。会员次卡消费回到扣次流程编辑。删除次卡消费后重算关联余次与流水。

### 5. 员工管理

工作台 → 员工 → 搜索/状态筛选 → 新增（姓名、账号、初始密码） → 成功 → 编辑资料 / 停用 / 重置密码。

账号为 3–32 位，以字母开头，允许数字、下划线、连字符。新建密码至少 6 位。编辑时账号和岗位不可修改。岗位固定店员。重置密码二次确认输入；停用或重置密码后原登录行为以服务端规则为准，原系统文案明确重置导致旧登录状态失效。

## 当前原型的交互覆盖和限制

可点击：四主入口；搜索、会员分类；会员新增编辑；开卡；扣次核对与结果；次卡补次/设置余额/状态变更；消费日期与类型查询；消费新增编辑删除；员工新增编辑/状态/密码重置；昵称编辑；协议结构；退出登录。

已覆盖：加载、空数据、加载失败；表单必填与业务校验；提交失败保留；提交禁用连点；无可用卡；作废卡；删除确认。

未展开：会员性别/来源高级筛选和排序、次卡流水高级筛选、短信状态筛选、短信未配置与发送失败的独立画板、员工创建完成后的凭据交接方案、头像选择、协议真实长文、真实分页和加载更多。Figma 阶段必须补充这些画板或状态。原系统高级筛选能力保留，不因原型未展开而删除需求。

不模拟：真实登录权限、网络并发余额冲突、重复请求幂等、后端数据删除限制、短信投递、真实文件上传、退出服务端会话。其规则需要联调验证，不以本地成功演示作为验收依据。

## 评审要点

1. 四个主入口是否清楚；常用操作是否覆盖店长最高频任务。
2. 会员档案默认展示次卡，是否符合门店实际使用。
3. 消费查询归并、保留笔数口径是否正确。
4. 微信昵称/微信号仍必填是否符合当前业务；本版先沿用。
5. 扣次是否需要独立核对；补次/手工调整原因是否应必填。
6. 平台运营是否应只对平台管理员开放；当前标为待确认。
7. 原型未展开的高级筛选、短信失败和分页是否应进入首版 UI 设计。
8. 会员、次卡、消费、流水之间的删除与改动规则需与后端核对。

先评审以上结构与规则，再在 Figma 中做设计语言、组件与高保真界面。此时不以灰度线框的边框、圆角和颜色作为视觉决策。
